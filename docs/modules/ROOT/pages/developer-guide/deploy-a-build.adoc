= Deploy

NeoDash runs on Kubernetes as one stateless Deployment, installed with the Helm chart in `k8s-deploy/neodash`. Each pod serves the UI, signs users in and runs the Neo4j queries; browsers never connect to Neo4j.

The full guide, with Keycloak set-up, Gateway API, network policies, upgrades and CI/CD, is `docs/deployment.md` in the repository. Every chart value is described in `k8s-deploy/neodash/README.md`.

== What you need

- Kubernetes 1.25+ and Helm 3.
- Neo4j 5, Community or Enterprise, reachable from the cluster, and a Neo4j user for NeoDash. Editors can run any Cypher as this user, so give it the access your editors need.
- An OpenID Connect provider such as Keycloak, with a confidential client (redirect URI `https://<host>/auth/callback`) and the roles `neodash-viewer` and `neodash-editor` assigned to users or groups.
- An Ingress controller or a Gateway API implementation, and a TLS certificate for the host.
- The NeoDash image, from the project's registry or a mirror of it.

== Install

The chart never takes credentials as values. Create the Secrets first:

[source,sh]
----
kubectl create namespace neodash
kubectl -n neodash create secret generic neo4j-credentials \
  --from-literal=username=neodash --from-literal=password='<neo4j password>'
kubectl -n neodash create secret generic neodash-oidc \
  --from-literal=client-secret='<client secret>'
kubectl -n neodash create secret tls neodash-tls --cert=tls.crt --key=tls.key
----

Then a values file with the minimum settings:

[source,yaml]
----
image:
  repository: <owner>/neodash
publicUrl: https://neodash.example.com
neo4j:
  uri: neo4j://neo4j.neo4j.svc.cluster.local:7687
  auth:
    existingSecret: neo4j-credentials
oidc:
  issuerUrl: https://keycloak.example.com/realms/acme
  existingSecret: neodash-oidc
ingress:
  host: neodash.example.com
  tls:
    secretName: neodash-tls
----

And install, from the published chart or from a checkout:

[source,sh]
----
helm install neodash oci://ghcr.io/<owner>/charts/neodash --version <chart version> -n neodash -f my-values.yaml
# or: helm install neodash k8s-deploy/neodash -n neodash -f my-values.yaml
helm test neodash -n neodash
----

The chart stops with a message if a required value is missing. `helm test` checks that the service answers and that NeoDash can reach Neo4j.
The session key, which encrypts the sign-in cookie, is generated on the first install and kept across upgrades; with GitOps tools that render charts offline, create it yourself and set `session.existingSecret`.

== Exposing it

The UI, the API (`/api`) and sign-in (`/auth`) share one host and path, and `publicUrl` must be the address users open.
By default the chart creates an Ingress for ingress-nginx with a larger request body (dashboards are saved as one document), a read timeout above the longest query and a larger header buffer (for the session cookie). For other controllers, set `ingress.className` and their equivalent annotations; for the Gateway API, set `ingress.enabled: false` and `httpRoute.enabled: true` with the Gateway in `httpRoute.parentRefs`.

== The image

- Distroless Node.js 22, running as UID 65532 with a read-only root filesystem, no shell and no capabilities.
- It makes no outbound internet requests: fonts, the UI, these docs and the map shapes for choropleth and area maps are all inside it. Map reports draw background tiles only if you set an internal tile server (`maps.tileUrl`).
- So it runs in air-gapped clusters: copy the image and the chart to registries the cluster can reach, and set `global.imageRegistry`.

== Running it

- Pods are stateless: scale with `replicaCount` or `autoscaling.enabled`. Upgrades are rolling and keep the old pods serving until the new ones are ready.
- `/healthz` is the liveness check; `/readyz` also checks Neo4j.
- Credentials are read at start-up: after rotating a Secret, restart the Deployment. Rotating the session key signs everyone out.
- Logs, including the audit lines, are JSON on stdout; see xref:developer-guide/roles-and-security.adoc[Roles, Security & Audit].

== Upgrading from upstream NeoDash

Dashboards don't need to change: they stay in Neo4j as `_Neodash_Dashboard` nodes, in the same format, and NeoDash 2.4 and this version can share a database while you move over.
Browser-side settings of upstream NeoDash (`config.json`, the `standalone…` settings, `ssoEnabled`, share links carrying credentials) no longer apply: the backend owns the connection, and the viewer role replaces standalone mode.
